# P5 / M6 交付：业务运营 / 投放（边际曲线 + 约束分配 + holdout）

## 1. 为什么不能按"平均 ROI 排序"加投

平均 ROI = 收入 / 花费。只要受众会饱和，收入对花费就是凹的，**平均 ROI 会随花费下降**——于是按平均 ROI 排出来的
"好 cell" 往往正是"下一元钱赚得最少"的那个。所以这一层的决策量必须是**边际回报**，而边际回报需要一条
从该 cell 自身历史拟合出来的曲线。

这也意味着数据必须能识别出曲线。演示数据的生成过程因此加了两件事（`scripts/build-demo-db.mjs`）：

1. **预算随时间波动**（缓慢正弦 + 季节），否则一个 cell 的历史只覆盖很窄的花费区间；
2. **边际递减**：`saturation = 1 / (1 + spend / K)` 作用在转化上，于是 `revenue` 对 `spend` 严格凹，
   平均 ROI 1.86、边际 ROI 中位数约为平均的 0.62。

数据生成过程写在脚本注释里，不是藏在某处——曲线的结论只能和它的数据一起被审查。

## 2. 曲线（`curve.ts`）

| 模型 | 形式 | 边际 | 何时 |
| --- | --- | --- | --- |
| `saturating` | `R = m·S/(1+S/K)` | `m / (1+S/K)²` | ≥8 点且比幂律拟合好 10% 以上 |
| `power` | `R = a·S^b` | `a·b·S^(b-1)` | ≥6 点 |
| `linear` | `R = m·S` | `m` | 点太少或没有曲率 |

拟合是确定性的：saturating 对 K 做网格搜索、m 有闭式解（固定 K 时模型对 m 线性）。选择规则要求额外参数
"用 10% 的 RMSE 换"，所以**恒定 ROI 的数据会被判成 linear，而不是被硬塞一个饱和参数**。

**这里抓到过一个会反转结论的 bug**：saturating 的解析边际被写成了 `m·K/(K+S)²`（差一个 K）。后果是每个饱和
cell 的边际 ROI 都≈0，优化器于是建议把它们的预算全部砍掉——数字看着自洽，方向完全相反。修完后验收里加了
**解析边际 vs 中心差分**的逐点比对（3 个花费水平 × 2 个模型），现在这条断言会直接抓住同类错误。

## 3. 分配（`optimize.ts`）

贪心边际均等 + 硬约束，选它是因为：曲线是凹的（收敛）、每一步的收益用曲线自身的积分 `predict(to)-predict(from)`
定价（不是线性近似）、约束是对步长的钳制（不满足就**报错**而不是返回一个违约的方案）。

约束：总预算守恒（≤1e-3 元误差）、每 cell 变动 ≤ ±50%、份额 ∈ [0.5%, 35%]。
结果给出每个 cell 的当前/建议花费、当前/边际 ROI（建议后也算一次）、曲线参数与 r²、预期收入增量；并统计
`boundHit`（是不是被约束卡住，而不是增益归零）。

一次实测：36 个 cell / 2 条查询 / 33 次步进，预计收入 5.80M → 6.70M（**+15.56%**），曲线噪声 62.7k，增益远高于噪声；
边际 ROI 的分散度从 6.52 收窄到 5.92（±50% 约束下无法完全均等，`boundHit` 会说明这一点）。

## 4. 可反驳：holdout（`holdout.ts`）

每个方案都带一个实验设计：处理组（加投的那个 cell）、对照组（同大区/同行业未加投的 cell）、观察 4 周、
需要检测的效应量、曲线的噪声、以及样本量算术 `n = 2(z_{1-α/2}+z_power)²σ²/Δ²`（α=0.05, power=0.8）。
`feasible` 直接比较所需与可用的 cell-月；不可行时 `note` 说"延长观察期或合并相邻地区"，可行时说"执行前需确认
这些 cell 可以按地区/账号拆分"。

## 5. 验收（`npm run verify:m6`，48 条断言）

- **数学**：凹数据判为 saturating（边际/平均 0.45）、恒定 ROI 判为 linear（1.00）、解析边际与数值导数在 6 个点上
  一致（相对误差 <1e-3）、`predict(0)=0`。
- **约束**：预算守恒；每 cell 变动在 ±50% 内；份额在 [0.5%,35%] 内；增益 > 曲线噪声；预算不变而收入投影更高；
  钱从低边际流向高边际（接收方均值 > 出资方均值 ×1.5）；边际分散度收窄。
- **可解释**：每个 cell 都带模型、参数、r²、点数、当前/边际 ROI；中位 r² 0.94；叙述里给出一个 cell 的曲线；
  叙述不含"保证/一定能/必然"。
- **可反驳**：holdout 的处理/对照/周期/效应/噪声/样本量齐备，`feasible` 与算术一致，`note` 给出可执行建议。
- **拒绝**：缺口径指标 → `not-in-model`；预算超出每 cell 边界 → `budget`；`maxChangePct=0` 且增益不敌噪声 →
  `unvalidated`。
- **确定性**：同数据两次运行，增益、每个 cell 的变动、SQL 序列完全一致。
- **经验**：`harvestFromCampaign` 沉淀 3 条 tip（边际 ROI、拟合差、可信幅度），带数值证据，可被检索。
- **CLI** 与库结果一致。

## 6. 这一阶段修掉的两个实现 bug

1. **saturating 边际少乘一个 K**（上面已述）——方向性错误，靠"解析 vs 数值导数"断言防回归。
2. **分配循环在有 cell 触边时原地打转**：选择 donor/receiver 时没有排除已触边的 cell，循环一直 `continue` 到
   guard 耗尽，`iterations` 只报 1 次、方案几乎没有移动。修法是只在"还能动"的 cell 里选，且两侧都空时
   `boundHit=true` 退出。

## 7. 诚实的限制

- **曲线是外推**：只在历史 spend 区间内被数据支持；±50% 是业务约束，不是统计学结论。
- **holdout 是提案**：样本量用的是两组均值比较的近似，没有做聚类/面板设计；能否拆分地区要 media 团队确认。
- **不做整数分配、跨指标权衡**（例如同时优化收入与新客），那是求解器形状的问题。
- **未做因果识别**：没有实验数据时，曲线里混着季节、竞品、素材变化；`limits` 里明说"先按 holdout 验证再全量"。
- **数据是设计的**：饱和与预算波动是为演示而构造的生成过程；真实数据上曲线形状、显著性与可行性都要重新判断。
