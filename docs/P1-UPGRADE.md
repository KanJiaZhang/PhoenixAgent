# P1 升级：四个欠账，四种证据

> 这四件事是在"竞争分析"里被点出来的四个欠账：图**声称了但没出力**、语义模型**没有版本纪律**、
> 决策层**只有单点算法没有平台**、问数面**只能听懂窄语法**。每一件都补成了可运行、可验收的模块，
> 并且每一件都在写的过程中抓到了自己的 bug——下面如实记录。

| 补齐的欠账 | 模块 | 关键数字 | 验收 |
| --- | --- | --- | --- |
| 图真正出力（结构特征 → AUC 增量） | `agents/risk/graph.ts` + `graph-report.ts` + `model.ts` | 基线 AUC 0.9613 → **0.9733（+0.0120）**；单特征最高 0.6986；基座遍历 **40/40 一致** | `verify:p1graph` 28–29 |
| 语义模型的版本与漂移 | `semantic/version.ts` | 变更分级、漂移对账（7 表/34 列）、shadow 10% → **hold** | `verify:p1ver` 33 |
| 决策平台化（冲突/容量/双签/下发） | `risk/conflicts.ts`、`risk/capacity.ts`、`campaign/writeback.ts`、`RiskApprovals(quorum)` | 重复规则 Jaccard **1.0**、不可达 1 条；200 单/天 → **6 人**（ρ=0.83）；同一人二次签名被拒；幂等键 `f4bbf4f4…` | `verify:p1dec` 45 |
| 混合问数（提案→校验→词表学习→多轮） | `semantic/ask/hybrid.ts` | 非法提案被拒并**明示降级**；`毛利→gmv` 学一次后**无 LLM 也能答** | `verify:p1ask` 42 |

验收总量：主 10 套 415 条 → **14 套 563 条**，`tsc --noEmit` 干净，四个案例 73 项自检不变。

## 1. 图终于出力了（P1-a）

### 1.1 之前的问题

`risk_event` 里有 `account_id / device_id / ip_id` 三列，四个案例**一次 `GraphClient` 都没调用**。
"用了图"是一句没有数字支撑的话。

### 1.2 数据与口径

| 改动 | 做法 | 为什么这样做 |
| --- | --- | --- |
| 事件加三列 | `account_id / device_id / ip_id` | 没有实体 id，就没有边 |
| 生成器分配实体 | **FNV 哈希事件 id**，不消耗 `random()` | 主随机流不动 → 15,188 事件 / 449 欺诈 / z=6.042 等全部数字保持逐字节不变 |
| 种入团伙结构 | 45% 的欺诈事件被路由到 5 台设备 / 3 个 IP；5% 的正常事件也碰这些设备 | 有信号，但**不是完美标签**（正常的共享设备/受害者也在这张网里） |
| 快照时点 | 取**上个月最后一天**（`snapshotCutoff`） | 决策时点能加载的最新结构；当月的边一律不可见 |

### 1.3 五个特征，全部是结构量

| 特征 | 含义 | AUC |
| --- | --- | --- |
| `g_component_size` | 同连通分量里的账户数 | **0.6957** |
| `g_two_hop_accounts` | 两跳内（同设备/同 IP）的不同账户数 | **0.6958** |
| `g_device_degree` | 用过的不同设备数 | 0.6794 |
| `g_shared_device_max` | 任一设备上的最大账户数 | **0.6986** |
| `g_pagerank` | 账户-设备-IP 二分图上的 PageRank ×1000 | 0.3004 |

`g_pagerank` 低于随机（0.30）**如实保留**：团伙伴的账户数量很少、入度高的是正常的高频账户，
所以中心性在这个结构里不是风险信号。它留在特征表里，是因为"我们只保留好看的特征"比"留下一个难看的特征"更危险。

### 1.4 增量：同数据、同求解器，只多一块特征

| 模型 | 特征 | holdout AUC |
| --- | --- | --- |
| 基线 | log(amount) + 7 个快照特征 | 0.9613 |
| + 图 | 同上 + 5 个结构特征 | **0.9733** |
| 增量 | | **+0.0120**（3,557 事件 / 155 欺诈） |

### 1.5 三条"不能作弊"的检查

1. **标签独立性**：把全部标签翻转后重算特征，**10,813 个事件的特征逐个不变**。任何"邻居欺诈率"式的特征都会在这里挂掉。
2. **PIT**：每个快照的 `as_of` 都早于它服务的事件；违规 0 次。而"同月快照"版本对 90%+ 的事件违反日期规则——
   它的 AUC 反而**更低**（0.6759 vs 0.6986），所以"模型质量看着没问题"永远不能当作泄漏的反证。
3. **两个引擎同口径**：把最新快照发布到基座（4,058 账户 / 14,576 边），抽 40 个账户用 gremlin 遍历
   `g.V('<acct>','Account').out('UsesDevice','UsedIp').in('UsesDevice','UsedIp').dedup()`，
   与本地 BFS **40/40 一致**（耗时 88s，其中大部分是写 1.4 万条边）。

启动方式：`PAGENT_GRAPH_CROSSCHECK=1 npm run verify:p1graph`（默认跳过，因为要写基座）。
发布会在基座目录留下 `pag-risk-graph.json`，脚本结束前会删掉——**基座仓库不留我们的文件**。

### 1.6 抓到的 bug

| bug | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 快照早了一个月 | `snapshotCutoff('2024-03-01')` 返回 `2024-01-31` | `Date.UTC(year, month-2, 0)` 是"上月 0 日"再退一个月 | 改 `month-1`，并用闰年断言钉住 |
| 一个人人相连的图 | 最大连通分量 = 4,068 / 4,039 个账户，所有结构特征跌到 0.53 | 生成器给每个事件从 400 个 IP 里随机取，IP 把整张图连成一块 | 普通账户用家庭 IP，只有 1% 走 NAT 池 |
| 我自己的断言过头 | "组件大小一定是最强特征"——实际 0.6957 < 0.6986 | 四个结构量高度共线 | 放宽为"与最强相差 <0.02"，并在文档里写明共线性 |
| 一个错误的假设 | "泄漏快照一定拿到更高 AUC" —— 实测更低 | 同月的边主要是事件自己带来的，反而稀释了正常账户 | 断言改写成"质量不能用来发现泄漏，日期才能" |

### 1.7 诚实的限制

- **团伙是种进去的**：增量是这条管线的**上界**，证明的是"结构 → 快照 → 增量"这条链路能工作，不是真实世界的增益大小。
- 快照粒度是月；真实的设备图谱要按天甚至按小时滚。
- 只有结构量，没有标签传播（那是另一门技术，且天然有泄漏风险）。

## 2. 语义模型的版本纪律（P1-b）

### 2.1 变更分级（机械规则，不看"看起来大不大"）

| 变更 | 级别 | 理由 |
| --- | --- | --- |
| `expression / formula / crossFact / aggFunction / filters / tables` 变了 | **breaking** | 定义动了，所有经过它的趋势在发布点台阶式跳变 |
| `column / level` 变了（维度重绑） | behavioural | 数字对，分组变了 |
| 新增指标/维度/列、描述变更 | compatible | 纯增量 |
| 删除，且**有消费者** | **breaking**（并列出消费者） | 查询会直接拒绝 |
| 删除，无人引用 | behavioural（上账但不拦） | 记录在案，不影响发布 |

### 2.2 漂移：拿仓库当参照，不拿模型自证

`driftReport(model, live)` 用 `PRAGMA table_info` / `information_schema`：
缺表、缺列、类型变化 → **blocking**；仓库多出的列、未建模的表 → 记录但不拦。
演示仓库：**7 表 / 34 列，0 阻塞**。合成漂移（删 `spend`、把 `DECIMAL` 改成 `TEXT`）都被抓到。

### 2.3 shadow：同一个问题，两个版本并排跑

```
spend 表达式 ×1.1  →  最大相对变化 0.1000  →  verdict = hold
两个版本完全相同    →  rowsChanged 0      →  verdict = promote
新版本删掉了指标    →  下一版拒绝回答     →  verdict = hold
```

### 2.4 发布门（`releaseGate`）

| 输入组合 | 结果 | 理由 |
| --- | --- | --- |
| compatible + 无漂移 + shadow 一致 | `promote` | |
| 有阻塞漂移 | **`reject`** | 仓库和模型已经不一致，diff 好坏无关 |
| breaking 但**没跑** shadow | `hold` | "没有证据的破坏性变更"不是发布 |
| breaking + 有一个 shadow 被 hold | `hold` | 任一问题移动就拦 |

### 2.5 抓到的 bug

| bug | 现象 | 修法 |
| --- | --- | --- |
| 只读守卫挡住了目录读取 | `PRAGMA table_info` 被 `assertReadOnly` 拒绝（守卫的正确行为） | verify 改用 `readSqliteCatalog()`（profile 阶段本来就有的目录读取），不走 SQL 通道 |
| 无类型列误报漂移 | 抽取器没给出 `dataType` 的列被当成 `text` 去比 `INTEGER` | 无类型时只查存在性，不比类型 |
| 计数口径 | 关系候选也被算进"表/列"计数 | 计数按 id 前缀分开，文档写清"关系 238 条"含关系实体 |

### 2.6 诚实的限制

- shadow 是**进程内并排执行**，不是流量切分；真正的灰度要在网关层按比例路由。
- 没有自动回滚：`reject/hold` 只是拒绝发布，回滚仍是人工操作。
- 类型比较用 SQLite 的 affinity 映射；换到 Snowflake/BigQuery 要换成 `information_schema` 的真实类型体系。

## 3. 决策层从"单点算法"到"平台"（P1-c）

### 3.1 规则集是系统：重复、空洞、冲突

窗口 2025-07 起（3,757 事件 / 155 欺诈，与案例 2 同一窗口）：

| 现象 | 证据 |
| --- | --- |
| R001 与 R002 几乎不相交 | 共享命中 **1** 次，Jaccard 0.0013 |
| 同谓词的另一条规则 = 重复 | `R001/R001-dup` Jaccard **1.0** → `merge` |
| 更紧的阈值是子集 | `R002-tight` 完全落在 R002 里（onlyB = 0）→ `superset` |
| 同谓词、不同动作 = 冲突 | `R002/R002-review` 既重复又在 774 个事件上动作相反 |
| 阈值高到无人触发 | `R-unreachable` 命中 0 → `drop` |
| 边际贡献不重复计数 | lone 之和 ≤ 并集欺诈数（additivity 通过） |

### 3.2 容量：这条规则配几个审核员

`capacityPlan` 用 Erlang-C（闭式、可手算）：

| 场景 | 利用率 | 平均等待 | SLA(4h) | 结论 |
| --- | --- | --- | --- | --- |
| 40 单/天 × 12 分钟，3 人 | 0.33 | 0.009h | ≈1.0 | ok |
| 200 单/天 × 12 分钟，6 人 | 0.833 | **0.1175h（7.1 分钟）** | ≈1.0 | ok，最小人数 6 |
| 同上，7 人 | 0.714 | 0.0324h（1.9 分钟） | ≈1.0 | ok |
| 400 单/天 × 12 分钟，3 人 | **3.33** | **∞（拒绝估算）** | 0 | understaffed，需要 11 人 |

饱和时**返回无穷并拒绝给一个"大概 3 小时"的数**——这是这个仓库一贯的做法。

### 3.3 双签：两次签名必须是两个人

`RiskApprovals(workspace, graph, { quorum: 2 })`：

- 同一人第二次签名 → **抛错**（`has already approved`），不是记两条；
- 一条签名 → `state.decision = null`、`decisions()` 为空（不发布）；
- 两个不同人 → `approve` 且 `decisions()` 里带着两个名字；
- 拒绝（reject）**不受 quorum 影响**，立即生效；
- quorum = 1 时行为与旧版一致（低风险决策照旧）。

### 3.4 方案下发：幂等键 + 二次校验 + 干跑

| 检查 | 证据 |
| --- | --- |
| 幂等键只取决于"要发的那些 cell" | 重排 cell 顺序 → **同一个键**；改 1 元 → **不同的键** |
| 手改 payload 会被抓 | 把 500 改成 999：`total-mismatch` + `bound-violated` |
| 默认不落地 | `status = dry-run`；只有 `commit: true` 且适配器校验通过才 `committed` |
| 回执 | `receiptId` 与 `acceptedAt` 随结果返回，供对账 |
| **我们自己的幂等记录** | `IdempotencyStore` 把提交过的键与回执落盘；同一个键再提交返回 `replayed` 与**原回执**，平台只被调用一次（验收里用请求计数证明）；同一个键配不同载荷 → 拒绝（键碰撞或推导出错，不能猜） |

### 3.5 抓到的 bug

| bug | 现象 | 严重性 | 修法 |
| --- | --- | --- | --- |
| **payload 自带"我合规"的结论** | 手改后的 payload 继承了构建时的 `checks: {ok:true}`，一路干跑到平台 | 🔴 高（这是这条链路的核心风险） | 抽出 `checkPayload()`，`submitWriteback` **重新算**而不是信 payload 里的 checks |
| 测试参数本身饱和 | 两组 Erlang 参数都超过 1.0，等待都是 ∞，比值毫无意义 | 🟡 中 | 换成 ρ=0.83 vs 0.71，断言才有内容 |

### 3.6 诚实的限制

- 冲突/重复只在**一个窗口**上判定；两条规则可能只在别的时间段重叠。
- 动作只区分 `block/review/challenge`，"先 block 再 review"的顺序语义没有建模。
- Erlang-C 假设泊松到达与指数服务时间；欺诈队列是突发性的，所以等待时间应读作**下界**、人数应读作**下限**。
- 下发适配器是接口 + 干跑实现，没有接任何真实投放平台 SDK；幂等键的**兑现**要靠平台侧去重。

## 4. 混合问数：模型可以提议，但决定权在校验器（P1-d）

### 4.1 链路

```
问题 ──► 词表改写（学过的词） ──► LLM 提案（可选） ──► 确定性校验（同一个 translate） ──► 执行 ──► 答案
                                        │                      │
                                        └─ 提案被拒 → 明示 fallback → 用确定性解释器作答
```

### 4.2 校验器抓到的东西

| 提案 | 结果 |
| --- | --- |
| `metric: "spend"`（用名字而非 id） | 修成 `metric/spend`，记录 repair |
| `topN: 5000` | **丢掉**而不是截断（截断等于替用户做决定） |
| `period: {said: "上个月"}` | **拒绝**：提议里的期间必须给 `from/to`，自然语言期间只由确定性解析器产出 |
| `metric: "metric/profit"`（不存在） | 拒绝，并列出 18 个可用指标 |
| GMV + `dim/channel`（不可切） | 拒绝（`not-in-model`） |
| 提案非法、但确定性解析器能答 | 作答，但 `source.fallback = 'proposal-refused'` |

### 4.3 词表学习：一次审查，长期生效

```
"毛利" → 拒绝（no-such-metric）
learnWord("毛利" → metric/gmv, evidence: "asked 2026-10-26, agreed with finance")
"毛利" → gmv，source.kind = deterministic（LLM 关着）
```

两条硬规则：目标 id 必须**存在**；同一个词**不能指向两个目标**（抛错，而不是在提问时按"最长匹配"猜）。

### 4.4 多轮：跟进句是增量

| 轮次 | 问题 | 结果 |
| --- | --- | --- |
| 1 | 2025 年 11 月各大区花费 | spend × region × 2025-11 |
| 2 | 那按月呢 | **保留** spend 与期间，换成 `dim/month` |
| 3 | 换成收入 | **换成** revenue，其余保留 |
| — | 没有上一轮时的"那按月呢" | **拒绝**，不当成新问题重复回答 |

### 4.5 抓到的 bug

| bug | 现象 | 修法 |
| --- | --- | --- |
| 正则丢了反斜杠 | `/^d{4}-d{2}-d{2}$/` 匹配不到任何日期，所有 LLM 期间都被拒 | 换成 `[0-9]{4}` 写法（和之前 `monthWindow` 那次是同一类事故） |
| 跟进句被旧指标"抢走" | `"spend 换成收入"` 里 `spend`（5 字符）比 `收入`（2 字符）长，最长匹配把 metric 解析回了 spend | **先单独解析跟进句**；它自己没指标时才前置旧指标 |

### 4.6 诚实的限制

- 学习需要人给出**词**（`learnWord(word, target)`），没有做自动词抽取——自动抽取正是最容易出错的一步。
- 多轮只处理指标/维度/期间/粒度的增量，不处理指代（"它的趋势呢"）。
- 提案质量取决于提示词与模型；本仓库的默认（`PAGENT_LLM=none`）不依赖它。

## 6. 接口面：四个模块上了线（P1-e）

九个新路由，全部沿用既有三件事：角色、确认令牌、逐请求审计。目录 `/v1/tools` 仍然由路由表生成，
所以 MCP（读目录）与 Console 自动看见它们——没有第二份清单。

| 路由 | 角色 | 它做的事 | 需要一个 token 吗 |
| --- | --- | --- | --- |
| `POST /v1/semantic/version` | viewer | diff 上一版 → 仓库漂移 → 同一问题 shadow → 发布门 | 否（只读） |
| `POST /v1/semantic/shadow` | viewer | 两个版本并排跑，返回行级移动与 promote/hold | 否 |
| `GET /v1/semantic/lexicon` | viewer | 已学过的词 | 否 |
| `POST /v1/semantic/lexicon` | analyst | 学一个词（目标必须存在；同词不可二指 → 409） | 否（但记 actor） |
| `POST /v1/ask/hybrid` | viewer | 问题 →（可选）提案 → 确定性校验 → 答案；带 `followUp` 续会话 | 否 |
| `POST /v1/graph/features` | viewer | 5 个结构特征 + AUC + holdout 增量（约 5 秒） | 否 |
| `POST /v1/risk/conflicts` | viewer | 规则集：重复/子集/冲突/不可达/边际 | 否 |
| `POST /v1/risk/capacity` | viewer | Erlang-C 容量，饱和时拒绝估算 | 否 |
| `POST /v1/campaign/writeback` | analyst | 生成下发载荷；默认干跑 | **提交需要 owner + token** |

三个"读不了就写"的边界，都在服务端而不是文档里：

| 边界 | 行为 |
| --- | --- |
| `graph/features {crossCheck:true}` 会写入基座 | **403**（要 owner） |
| `writeback {commit:true}` 没有 token | **428 `confirm-required`**，返回同一份 plan 的 token 后再发 |
| `writeback {commit:true}` 没有平台端点 | **501 `no-writeback-endpoint`**——宁可拒绝，也不伪造一张"已提交"的回执 |

令牌是**绑定到计划本身**的（`planHash`）：预算或 `maxChangePct` 变一个字，旧 token 就失效。
下发载荷的 `idempotencyKey` 在干跑与提交之间**保持不变**，所以"先看后发"是同一个请求，重放不会变成两笔预算。

Console 多了第五个工作台「发布与决策」：发布检查、规则冲突表、容量、图特征、混合问数与跟进、下发干跑/提交。

### 6.1 接线时抓到的两个 bug

| bug | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| **分币舍入被当成预算错误** | 36 个 cell 的写入被 `total-mismatch` 拦下，总差 0.18 元 | 校验容差写成 0.01，而 36 次四舍五入最多漂 18 分 | 容差 = `0.005 × cell 数 + 0.01`，并把理由写进代码 |
| 触边被误判为越界 | 恰好 +50% 的 cell 报 "move 0.5 exceeds 0.5" | 先舍入到分再算比例，得到 1.5000000000000002 | 引入 `BOUND_EPSILON = 1e-6` |

另外改了一处 **HTTP 语义**：agent 拒绝给出方案（例如把预算砍到 200 万会让收入损失超过噪声）时，
路由返回 **409 `agent-refused`** 并带 agent 自己的理由，而不是返回一个 cell 为空、键却合法的载荷。

## 7. 灰度：sticky 分桶 + 自动回滚（P1-f）

`shadowAsk` 回答"发布前数字会不会动"，这一层回答"发布后谁在用新版本、什么情况下停下来"。

| 性质 | 做法 | 怎么验 |
| --- | --- | --- |
| **粘性，不是随机** | 桶号 = `hash(actor, question) % 100` | 同一个人问同一个问题永远在同一侧；1,000 个桶在 30% 下命中 **300** |
| **服务的是快照** | 灰度侧加载 `v<to>.json` 的索引 | 灰度 actor 的回答带 `modelRevision: 2`，数字恰好比稳定侧高 10% |
| **晋升要有证据** | 答案 ≥ 30、错误率 ≤ 2%、且 shadow 没移动数字 | 1 条回答 → 拒绝并说明差多少；30 条 + breaking 变更 → 要求先跑 shadow |
| **breaking 必须带 shadow** | 两个快照 diff 是 breaking 且没给问题 → 拒绝 | 错误信息点名"改了几处定义" |
| **回滚是决定** | 必须给 reason；写进配置与事件日志 | 无 reason → 400；有 → `rolled-back`，桶不再生效 |
| **连续 3 次失败自动停** | 灰度侧的**拒绝也算失败**（把能答的问题答成拒绝，就是回归） | 三次拒绝后 `status: rolled-back`、`auto: true`、actor = `canary-guard` |

"拒绝算失败"是这一层唯一有争议的设计，选择它的理由：一个把答案变成拒绝的版本，与一个抛错的版本对用户是同一件事，
而后者更容易被监控发现。所以两者都记 `error`，都计入自动回滚。

### 7.1 抓到的 bug

| bug | 现象 | 修法 |
| --- | --- | --- |
| `require` 在 ESM 里不存在 | 灰度启动直接 500/409，错误信息只写着 "require is not defined" | 顶层 import `writeFileSync`（这是从 CommonJS 习惯里带出来的） |
| 证据按"所有历史"统计 | 第二轮的 canary 会把第一轮的答案算进自己的证据 | 只统计**最近一次 `start` 之后**的事件 |
| 测试断言写错了消息来源 | "1 条回答不能晋升"实际被 breaking-diff 规则拦下 | 断言放宽到任一理由，另加一条对 `canPromote` 的直测——规则属于 store，不属于路由 |

### 7.2 诚实的限制

- 桶函数是 FNV 哈希，不是加密哈希：知道 actor 与问题就能预测落在哪一侧（这是特性，不是缺陷——可复现优先）。
- 没有按维度切流量（"只灰度华东"）：需要 `bucket(actor, question, dimensionValue)` 的第三维，还没做。
- 自动回滚只看错误，不看**质量**（数字对不对）：后者要靠 shadow 或 holdout，不在这一层。
- 事件日志是单文件 append-only，并发写依赖操作系统；生产要换成带锁/队列的写入。
