# 四个端到端 Agent 案例

这份文档收录四个可以**真跑**的 Agent 实例：跑的是真实语义模型、真实数仓、真实 agent 模块，每一步自检，不满足就退出非 0。
每个实例都是「**声明**（`agents/*.agent.json`，含门禁与预算）+ **运行器**（`examples/*.mjs`）+ **产物**（`.pag/examples/*/artifacts/`）」，
声明不是装饰：门禁与预算从 JSON 读，改一处 JSON 运行器就跟着变。

```bash
npm run example:risk       # 案例 1：风控策略（建规则）        17 项自检
npm run example:audit      # 案例 2：风控策略巡检（管规则）     12 项自检
npm run example:growth     # 案例 3：归因 + 市场决策（同预算重分配） 23 项自检
npm run example:stoploss   # 案例 4：止损归因 + 砍预算（少花钱） 21 项自检
npm run examples           # 依次跑完四个
```

## 一览

| # | 实例 | 域 | 一句话问题 | 核心机制 | 关键实测 | 自检 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `risk-strategy` | 风控 | 哪些特征真的有效？给我一条能上线的规则 | 趋势 → 特征（PIT 硬门）→ 规则合成 → holdout 回测 → 人工审批 | P=0.857 R=0.338，增量召回 +8.45%，审批前 published=0 | 17 |
| 2 | `risk-rule-audit` | 风控 | 现有规则还值得留着吗？下线会少抓多少 | 命中/精确率/召回、Jaccard 重叠、每天拦截容量、特征 PSI 漂移 → keep/retune/retire | R001 retire（只丢 3 个欺诈）；R002 retune（召回主力 73.5%，阈值无解） | 12 |
| 3 | `attribution-campaign` | 增长 | 花费为什么涨？同预算该往哪调 | 归因循环（批量下钻、显式残差）→ 边际响应曲线 → 约束分配 → holdout | 变动 2.64M、残差 0；预计收入 +902.5k（噪声 62.7k） | 23 |
| 4 | `growth-stop-loss` | 增长 | ROI 被摊薄，该砍多少、砍哪里、怎么验证 | 比率两因子 → 跨事实口径校验 → **利润目标 + 预算上限**（允许不花满）→ switchback | 收入 −475.7k 而利润 **+787.4k**，留出 752.2k 未花 | 21 |

四个案例刻意覆盖**四种不同的工作流**：建规则、管规则、把预算花得更好、把预算花得更少。

## 案例 1：风控策略（建规则）— `risk-strategy`

**问题**：「最近欺诈趋势如何？哪些特征真的有效？给我一条可以上线的规则，并告诉我它在离线上能抓多少。」

### 流程与实测

```
[1] 路由   agent=risk type=detective confidence=1（依据：欺诈、风控、规则、特征）
[2] 趋势   大区 3 在 2025-07 出现拐点：2.52% → 6.75%（z=6.042，样本 2854/934）
[3] 特征   可用 8/9；剔除未来函数 f_chargeback_30d（AUC 0.9355，as_of > event_date 15188 处）
           主特征 model_score_v1：AUC 0.9435 / KS 0.7668 / IV 3.9589 / PSI 0.038 / 单调递增
[4] 规则   2 条候选；首选 `f_blacklist_hit = 1`
[5] 回测   holdout P=0.8571 R=0.338 覆盖 1.49% lift 22.64（TP 24 / FP 4）
           对存量规则：新增抓到 6 个欺诈、重叠 67.9%、增量召回 8.45%
[6] 审批   审批前 published=0 → risk-lead@demo 批准 → published=1（带审批人与时间）
[7] 经验   3 条 tip：特征有效性 / 规则回测 / 未来函数教训，全部带数值证据
```

### 自检（17 项，节选）

- 路由到了风控并给出依据，不是一个标签；
- 拐点在注入月 ±1 个月内且 `z ≥ minZ`（`minZ` 来自 manifest）；
- **未来函数被 `as_of_date > event_date` 硬门拒绝**，哪怕它是全文件 AUC 最高的特征；
- 规则 ≤3 条件、holdout 达到声明的 precision/recall 门、混淆矩阵自洽、对存量规则有增量；
- **Agent 绝不自动发布**：批准前 `published=0`，批准后才出现；
- 教训带数值进入 Skill 库，并可被检索。

### 什么会推翻它

把 `minPrecision` 提到 0.9（规则被门禁拒掉，Agent 回退到"不推荐"）；把 holdout 换成上游还没回填标签的月份（只剩噪声）；删掉 `f_blacklist_hit`（只剩弱特征，精确率掉到 0.5 以下）。

**产物**：`trend.json`、`features.json`、`rules.json`、`approval.json`、`skills.json`

> 「PhoenixGraph 用在哪 / SQL 怎么验 / 规则怎么验」见 **[CASE-1-VERIFICATION.md](CASE-1-VERIFICATION.md)**；

## 案例 2：风控策略巡检（管规则）— `risk-rule-audit`

**问题**：「现有风控规则还值得留着吗？哪些在重复拦截、哪些该重拟合、哪些该下线？下线会少抓多少？」

这是**另一个工作流**：规则已经存在，任务是治理。规则库会腐烂——重叠、漂移、精确率下降——需要用新窗口的数据定期复核。

### 流程与实测

```
[1] 路由   agent=risk type=detective
[2] 巡检   2025-07 ~ 2025-12（3757 事件 / 155 欺诈 / 168 天）
[3] R001 `amount >= 5000 AND f_new_device_flag = 1`
       命中 12 · 精确率 0.25 · 召回 0.019 · 覆盖 0.32% · 每天拦截 0.07
       与 R002 重叠 0% · 独占抓到 3 个欺诈 · 特征漂移 PSI=0.003
       判定: retire（精确率 0.25 低于门槛 0.5）
[3] R002 `f_login_fail_7d >= 3`
       命中 774 · 精确率 0.147 · 召回 0.7355 · 覆盖 20.60% · 每天拦截 4.61
       与 R001 重叠 0% · 独占抓到 114 个欺诈 · PSI=0.002
       阈值无解: 即使收到最紧（f_login_fail_7d >= 5），精确率也只有 0.3111（门槛 0.5）
       判定: retune（精确率低，但它是召回主力：独占 114 个欺诈，占 73.5% → 上调阈值而不是下线）
[4] 建议   下线 R001（每天少 0.1 次拦截，需人工确认误杀影响）
[6] 代价   剩余召回 73.55%，只少抓 3 个欺诈，每天少 0.07 次拦截
[7] 守护   数据库里 R001/R002 仍然是 active —— Agent 没有改动任何状态
```

### 两个判断，写进文档而不是埋在代码里

1. **低精确率 ≠ 该下线。** R002 精确率只有 0.147，但它独占 73.5% 的欺诈；把它下线会让检测能力归零。
   所以判定规则是：低精确率 **且** 独占召回占比 ≥5% → `retune`；否则才是 `retire`。
2. **"重拟合"必须给出阈值，或者明说无解。** R002 的阈值扫描显示：收到最紧也只有 P=0.311，门槛是 0.5。
   于是输出「阈值无解，需要更强的特征或组合条件」——而不是一句空洞的"建议重拟合"。

### 自检（12 项，节选）

- 每条规则都有 `keep/retune/retire`，且非 keep 的必须带原因；
- 重叠用命中集合的 Jaccard（0..1），容量算出每天拦截次数，规则用到的每个特征都做了 PSI 漂移；
- 建议附带**下线代价**，且"少抓 N 个"只算真正会丢的（其他存活规则也抓到的、以及本来没人抓到的都不算）；
- **Agent 没有改动任何规则状态**（下线是人的动作）。

### 什么会推翻它

把 `holdoutMonths` 缩到 1（样本不足，精确率置信区间比结论还宽）；把 `minPrecision` 调到 0.1（R002 变成 keep，漂移也不再触发重拟合）；或者把 `driftThreshold` 调到 0.001（两条规则都因微小漂移被判 retune）。

**产物**：`audit.json`、`recommendation.md`、`skills.json`

## 案例 3：归因 + 市场决策（同预算重分配）— `attribution-campaign`

**问题**：「11 月花费为什么涨了？下一周期预算该往哪里调、调多少、怎么验证？」

### 流程与实测

```
[1] 路由   diagnostic（找原因）+ prescriptive（要动作）
[2] 归因   spend 2.27M → 4.91M，变动 2.64M（additive，残差 0）
           按 region：华南 925.6k（35.0%）、华东 694.5k（26.3%）、华北 604.0k（22.9%）
           按 channel：搜索 1.39M（52.7%）、信息流 755.5k（28.6%）、直播 494.8k（18.7%）
           下钻：spend → channel = 搜索 → industry = 美妆个护
[3] 比率   ROI 2.0347 → 1.4727：分子（收入）项 +0.5338，分母（花费）项 −1.0958
[4] 投放   预算不变 3.41M；预计收入 5.80M → 6.70M（+902.5k，15.56%，曲线噪声 62.7k）
           加投 华东/3C数码/直播 +35.6k（边际 2.847，平均 4.348）
           加投 华北/母婴/直播 +15.7k（边际 5.567，平均 6.514）
           减投 华南/3C数码/搜索 −151.2k（边际 0.275，平均 0.720）
[5] 验证   geoholdout 4 周，处理组按建议调整，所需 1 / 可用 11 → 可行
[6] 经验   7 条 tip（批量取数 42→9、优先下钻渠道、比率两因子、边际 ROI、曲线拟合、可信幅度）
```

### 自检（23 项，节选）

- 切片**加总等于变化量**（<1e-6），残差显式（本例 0），下钻至少两层，查询数 < 朴素切片数一半（9 vs 42）；
- 叙述**不含因果词**，并声明"是描述性分解"；
- 比率分解两项之和 = 变动，残差 0；
- 投放：**预算守恒**、每 cell 变动 ≤ ±50%、预计增益 > 曲线噪声、每个建议都挂曲线参数与 r²；
- holdout 有设计、有效应量、有样本量算术与可行性；
- 交接单四段齐全（发生了什么 / 怎么调 / 怎么验证 / 边界），不含"保证 / 一定能"。

### 一份真实的交接单（节选）

| 方向 | cell | 当前花费 | 调整 | 边际 ROI（平均） | 预计收入变化 |
| --- | --- | --- | --- | --- | --- |
| 加投 | 华东 / 3C数码 / 信息流 | 129.7k | +64.9k | 0.947（1.402） | 57.3k |
| 加投 | 华北 / 3C数码 / 直播 | 90.2k | +45.1k | 2.037（3.568） | 75.7k |
| 减投 | 华南 / 3C数码 / 搜索 | 302.4k | −151.2k | 0.275（0.720） | −50.7k |

### 什么会推翻它

把窗口换成两个季节相同的月份（变动接近噪声，归因只剩零散切片）；把 `maxChangePct` 改成 0（无法移动 → 投放 Agent 拒绝）；或者数据没有饱和（曲线被判 `linear`，边际≈平均，任何再分配都不产生增益 → 拒绝）。

**产物**：`attribution.json`、`campaign.json`、`handoff.md`、`skills.json`

## 案例 4：止损归因 + 砍预算（少花钱）— `growth-stop-loss`

**问题**：「ROI 被摊薄了，哪些 cell 在亏钱？该砍多少、砍哪里？砍了以后怎么验证不是把生意砍坏了？」

案例 3 是"同样的预算花得更好"，本案例是"少花钱但更赚钱"。为此补了两件事：

1. **优化目标可以是利润**（收入 − 花费），并且**预算从"总额"变成"上限"**——允许不花满，这才是止损的形状；
2. **砍量的实验设计是 switchback**（同一批 cell 按周交替），而不是地区对照——砍掉的花费会让地区需求差异混进结果。

### 流程与实测

```
[1] 路由   「为什么 11 月 ROI 被摊薄」→ attribution（diagnostic）
           「该砍哪些 cell」→ campaign（prescriptive）
[2] 归因   ROI 2.0347 → 1.4727（Δ −0.5620）
           分子（收入）项 +0.5338 · 分母（花费）项 −1.0958，两项之和 = 变动，残差 0
[3] 跨事实 采纳前 unvalidated → 采纳 metric/capture_rate 后：
           GMV 68.0k → 97.4k（+43.2%）；归因收入 4.61M → 7.23M（+56.9%）
           捕获率 1.48% → 1.35% —— 收入没有等比例变成成交
[4] 止损   预算上限 2.90M（原 3.41M）；提议花费 2.14M，**留出 752.2k 不花**
           收入 5.80M → 5.32M（−475.7k），**利润 2.39M → 3.18M（+787.4k）**
           砍 华南/3C数码/搜索 −151.2k（边际 0.275）、华东/3C数码/搜索 −131.8k（边际 0.300）、
              华北/3C数码/信息流 −109.9k（边际 0.252）
[5] 验证   switchback：同一批 cell 按周交替，观察 4 周，所需 1 / 可用 25 → 可行
[7] 经验   5 条 tip（批量取数 20→7、比率两因子、边际 ROI、拟合差的 cell、预算上限）
```

### 自检（21 项，节选）

- 两个子问题分别路由到正确的 Agent（"为什么"→归因，"该砍"→投放）；
- ROI 两项之和 = 变动且残差 0；分母效应为负（花费涨得比收入快）；
- **跨事实口径**：未采纳的 `metric/capture_rate` 被问数面拒绝（`unvalidated`），采纳后按区给出 4 行；
- **利润上升而收入下降**（+787.4k / −475.7k）——这是止损的定义，而不是矛盾；
- **花费不超过上限** 且确实有未花掉的预算；砍掉的 cell 边际 ROI 全 < 1；每 cell 变动仍 ≤ ±50%；
- **砍量用 switchback**，对照是"同一批 cell 的对照周"；
- 交接单写清「为什么摊薄 / 砍哪里 / 怎么验证」，并明确"留出不花的钱"。

### 什么会推翻它

把 `objective` 改回 `revenue`（Agent 会拒绝：收入下降，无法证明调整有利）；把 `budgetIsCap` 设成 false（预算必须花满，止损无从表达）；或者曲线没有饱和（边际 ROI > 1，砍任何 cell 都亏，Agent 不做建议）。

**产物**：`roi-attribution.json`、`cross-check.json`、`stop-loss-plan.json`、`handoff.md`、`skills.json`

## 四个案例共用的四条规矩

1. **每个数字都能被复核**：要么有手写 SQL 对账（案例 3/4 的切片、案例 4 的跨事实比值），要么有自洽等式（残差、混淆矩阵、预算守恒）。
2. **拒绝是答案**：门禁不达、预算不可行、没有共享维度、未审查的指标——都返回带 `hint` 的拒绝，而不是一个看起来完整的结论。
3. **人不被绕过**：风控规则发布要审批（案例 1），规则下线只给建议不改状态（案例 2），跨事实指标先采纳再问数（案例 4）。
4. **经验入库**：四个案例共沉淀 17 条 tip，每条带产生它的数值（查询数、份额、残差、精确率、PSI），可被后续检索。

## 边界（四个案例共同）

- 跑在同一份**演示数仓**上：真实环境里标签回填有延迟、特征仓有上百个特征、ROI 曲线会被竞品与素材打断。
  门禁与 holdout 正是为这些而设，但它们不能替代真实实验。
- 风控审批是**单签**（接口支持多条日志，流程未强制双签）；案例里都写明了审批人。
- 案例 3/4 的"预计增益/损失"是**曲线外推**，不是已实现的增量；交接单里都写了"先按 holdout 验证再全量"。
- 案例 2 的重叠度量用命中集合 Jaccard：两条规则可能针对不同人群但在这里看起来相似；容量只算命中次数，不含人工审核成本与误杀赔付。
