# P4 / M5 交付：智能归因（循环、批量、显式残差）

## 1. 归因的形状

```
node(metric, filters, depth)
  ├─ 1 条查询：两个期间的总量（带切片时同时给出该维度的全部切片）
  ├─ 选分解方式：模型支持哪种就报哪种
  │    ratio        —— 指标有分子/分母公式（ROI = revenue / spend）
  │    additive     —— SUM/COUNT 指标，且驱动的符号能从父指标表达式里读出来
  │    association  —— 有驱动但没有公式/符号：只报同向变动，不报份额
  ├─ 打分：贡献额、份额、是否低于报告阈值
  ├─ 剪枝：低于阈值的不展开
  └─ 下钻：份额最大的驱动（递归到该指标）或份额最大的切片（加过滤条件再切另一个维度）
```

三条硬规则，每条都在验收里被断言：

1. **精确优先。** 比率按 `Δr = (n1-n0)/d1 + n0*(1/d1 - 1/d0)` 两因子分解，两项之和就是总变动，残差为 0（断言 ≤1e-9）。可加指标按切片加总，`Σ切片Δ = Δ`（断言 ≤1e-6）。驱动带着公式里的符号：`GMV = SUM(amount - refund_amount)` 里 `refunded_amount` 的贡献是**负**的——不加符号就会得到"解释率 123%"这种荒谬结论（这次实现中真实踩到并修掉）。
2. **残差必须显式。** 去掉一个驱动，残差就以绝对值和份额出现，并在叙述与 `confidence.warnings` 里各说一次。不去凑 100%。
3. **拒绝优于编造。** drivers 模式没有 `contributesTo` 边、指标不存在、预算耗尽，都返回带 `hint` 的 refusal，而不是给一个"看起来完整"的树。

## 2. 性能：批量是设计要求，也是断言

需求 8 说归因里的子查询性能是关键点。做法与证据：

| 做法 | 效果（实测） |
| --- | --- |
| 一个维度一条查询（`GROUP BY period, slice`，两个期间一起） | region 4 个切片：**1 条**查询 vs 逐切片逐期 **8 条** |
| 每层只查需要的维度（默认 3 个，时间层级不作为切片） | spend 2025-10→2025-11 全程 **9 条** vs 朴素 **42 条**，2 ms |
| 预算（queries/ms/depth）在每层检查 | 预算耗尽 → refusal `budget`，不返回半棵树 |
| 切片下钻复用同一个渲染器，过滤器自动带出要 join 的表 | 二层子查询可执行（这次修掉了缺 join 的 bug） |

`cost` 里同时给 `queries` 与 `naiveQueries`，`SliceSet` 里给 `naiveQueries`/`batchedQueries`，所以"省了多少"是数字不是说法。

## 3. 解释（话术上的自我约束）

- 每句都带数值与份额；没有"显著"、"大幅"这类词。
- 比率分解**不给份额**（两项相抵，份额会荒谬），只给数值与方向，并在正文解释原因。
- 残差单独成句："另有 X（占 Y%）未被这次分解解释"。
- 固定 `limits`：`这是分解归因（descriptive decomposition），不是因果结论`；`贡献份额不说明驱动机制`；`阈值是报告阈值，不是统计显著性检验`。
- 验收断言：叙述含"不是因果结论"，且**不含**"导致/因为/造成/致使"。

## 4. 与 M4 的闭环（需求 8 的后半句）

`harvestFromAttribution` 从一次真实归因里最多沉淀四类 tip，每类都有运行证据：

| tip | 触发条件 | 证据 |
| --- | --- | --- |
| 批量取数 | `naiveQueries ≥ 2×queries` | 两个查询计数、迭代数 |
| 该指标优先按哪个维度下钻 | 某个切片份额 ≥50% | delta、切片 delta、份额 |
| 比率要按分子/分母分解 | 本次用了 ratio 分解 | delta、驱动数、残差 |
| 有残差就要说出来 | `|unexplained.share| > 1%` | delta、残差、份额 |

一次验收里的三个运行共沉淀 **6 条 tip**，全部带数值证据，可被 `advise` 检索到。

## 5. 验收（`npm run verify:m5`，45 条断言）

- **与基座一致**：`attribute_change` 在 TPC-H 上复现 `95,612,794.05 → 98,879,432.89`、`+3,266,638.84`，并自陈"贡献之和 = 变化量"（服务不可达时该段显式 SKIP，不假装）。
- **比率**：两因子、和等于变动、残差 ≤1e-9、两项反号、`shareMeaningful=false`。
- **可加**：region 切片 1 条查询（8 vs 1）、`Σ切片 = Δ`、3 层路径（`spend → channel = 搜索 → industry = 美妆个护`）、子集是带过滤的查询且能执行、9 条查询内完成。
- **残差**：全驱动残差 0；去掉 `paid_amount` 之外的驱动后残差 `-11.6%`，叙述与 warning 都报出；`refunded_amount` 的贡献为负。
- **拒绝**：`not-in-model` / `no-such-metric` / `budget` 三种，均带 hint。
- **确定性**：同问两次，delta、切片份额、SQL 序列逐字节一致。
- **技能**：6 条 tip、均带数值证据、批量/残差/比率三类齐备、可检索。
- **CLI** 与库结果一致，携带 10 条证据 SQL。

## 6. 诚实的限制

- **没有显著性检验**：只有 "报告阈值"（`pruneShare`/`expandShare`），因为 24 个月的数据做不了可信的检验；措辞里明确写"不是统计显著性"。
- **只沿 `contributesTo` 和 `groupedBy` 走**：没有探索式搜索（比如自动尝试所有维度组合），也没有反事实（"如果花费不变会怎样"）。
- **乘法关系没做**：`revenue = conversions × aov` 这类乘积分解没有实现；目前只有 ratio 与 additive，其余降级为 association。
- **切片下钻只走一条路径**：`topK` 固定为 1，并列候选不会都展开。
- **基座案例是集成验证，不是复算**：TPC-H 的数字来自基座自己的 `attribute_change`，本 Agent 在 demo 语料上自证分解与残差；两条路径共享语义层契约，但不是同一份数据。
- **成本模型粗糙**：`naiveQueries` 按"切片数 × 期间数"估算，不考虑一条查询内部的分区裁剪收益。
